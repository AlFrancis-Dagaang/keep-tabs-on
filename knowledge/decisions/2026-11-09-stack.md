# Stack

## Context
Kinsenas is a personal finance tracker for young Filipino employees who split their money across 3–6 accounts. It starts with the owner and 3–5 friends. It needs Google sign-in, per-user data isolation, atomic multi-row money actions, and an installable mobile-friendly web app. There is no offline mode, no native app, and no integrations beyond Google. The owner set the stack in the brief notes.

## Options
- **A (chosen):** Next.js (App Router), TypeScript, pnpm, Vitest, Tailwind CSS + shadcn/ui, Zod, Neon Postgres + Drizzle, Neon Auth (Google), Next.js built-in manifest for the PWA, Vercel.
- No alternatives were proposed: the brief does not call for offline, native mobile, heavy compute, or a fixed existing system.

## Decision
Option A. Server-side RLS follows Neon's documented pattern. The app connects as a role without BYPASSRLS on the WebSocket Pool driver. Each request runs in a transaction that sets the verified user's claims with `set_config('request.jwt.claims', …)`, and the policies use `auth.user_id()` via Drizzle `crudPolicy`. That same transaction makes multi-row actions atomic. Money is stored as integer centavos. Balances, progress and budget totals are computed from transactions. Budget limits are snapshotted per month in `budget_months`. Dates use Asia/Manila.

## Consequences
- Every data access must go through the per-request transaction helper. An owner-role connection in app code would bypass RLS.
- Migrations need the direct owner connection; the app uses a separate restricted role.
- Neon Auth is new and was rebuilt on Better Auth, so its package names and APIs may shift. Keep auth in one module. /scaffold should confirm the package and how the session's user ID maps to RLS claims.
- No service worker means no offline use, which is accepted for v1.
