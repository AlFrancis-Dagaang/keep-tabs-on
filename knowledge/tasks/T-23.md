## Findings
- Today a goal has two links. `transactions.goal_id` (Add money, a transfer into the goal's account, drives Saved, target cap, completion flash) and `set_aside_goal_id` (the For link, drives Set aside). Saved = `saved_before + sum(goal_id)`; Set aside = `sum(set_aside_goal_id) + set_aside_before`. Nothing adds them, which is what confuses.
- Going to one figure: figure = `goalSetAside` after the migration folds `saved_before` into `set_aside_before` and relinks `goal_id` transfers to `set_aside_goal_id`. Then `goal_id`, `saved_before` and (cleared) `account_id` are dead columns, left in place (additive, dropped later as backlog).
- Relink is safe against the checks: both columns are transfers; `transactions_set_aside` needs a transfer with exactly one set-aside link, and a row never has both (checked below). A relinked transfer becomes a plain transfer, so it is editable and removable in Activity (T-20 behaviour) and `isLinked`/the linked-payment editor no longer need the goal branch.
- Dev has no goals (read-only check, host `ep-rough-sea-ao6no8lf`: 0 rows, 0 transfers with both links), so the migration's data step is proven by a DB test, not by dev data. The owner's real goals live where the app is used: production, which I must not touch (CLAUDE.md). The migration reaches production through the Vercel build after the owner OKs the push.
- Touched code (all read from the repo): `goals/actions.ts` (`addToGoal`, `addedTransfers`, the saved-vs-target check), `goals/goal-form.tsx` (`AddMoney`, `AddFields`, the Saved in and Already saved fields, `GoalProgress`), `goals/page.tsx` and `goals/[id]/page.tsx` (account join, two bars, `AddMoney`, history query on `goal_id`), `(app)/page.tsx` (Overview goals `saved` sum on `goal_id`), `activity/actions.ts` (`editPayment` goal branch), `activity/entry-form.tsx` (reads goals for the For list, no change expected), `accounts/actions.ts` (goal blocks account delete), `app/setup/actions.ts` and `setup-form.tsx` (goals with an account), `lib/money.ts` (`isLinked` goalId) and its test, `lib/set-aside.test.ts`, `db/schema.ts`, `components/set-aside.tsx` (still used by bills, debts, installments).
- Installments (was T-24): bills already work this way (`PayBill` takes `accounts`, `payFields` has `accountId`, `payInput` validates it, balance check). The installment's fixed account is read in `installments/actions.ts` (field, schema, save's account lookup, `from` in `payInstallment`), `installment-form.tsx` (Account select, `PayInstallment` description "from {account}"), `installments/page.tsx` and `[id]/page.tsx` (inner join to accounts), `accounts/actions.ts` (delete guard), `db/schema.ts`. Both pages need `loadBalances` to feed the From list. `paidTo` already exists on the pay form; the To account is that field with a `<datalist>` of account names, so only `account_id` nullable changes in the schema.
- Both changes edit the delete guard in `accounts/actions.ts` and share migration 0015.
- Lessons applying: 2026-11-14 show a figure on real data (below); 2026-11-17 qualify outer table (no new raw SQL planned); 2026-11-17 DB test timeout (3 runs); 2026-11-14 check DB host before any DB command.
