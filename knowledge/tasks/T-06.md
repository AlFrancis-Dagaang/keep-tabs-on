# T-06: Goals

## Acceptance criteria
- [x] Create a goal with target, deadline, saved-in account and already-saved amount
- [x] Add money moves funds by recording a transfer linked to the goal into its saved-in account; both account balances update
- [x] Progress = already saved + linked transfers; history lists each transfer with from/to; the bar turns clay and flashes at target

## Findings
- Arch names the shape: `goals` (name, target, deadline, account_id, saved_before) and an optional `transactions.goal_id`. Progress is computed, never stored. Multi-row actions run in one `withUser` transaction.
- Goals copy debts (T-05) almost line for line: `actions.ts` with `FormState`, `debt-form.tsx`, the list page with a stretched-link row, and `[id]/page.tsx`. `progressBlocks` and `announceCompleted`/`useCompletedFlash` are already shared, and the sidebar already highlights `/goals/[id]` and sits in Suspense.
- The one real difference: Add money inserts a **transfer** (`account_id` = from, `to_account_id` = the goal's account, `goal_id`), not an expense. `balanceOf` already moves money for transfers, so both balances update with no new money logic. The DB check already refuses from = to.
- `saved_before` is only a progress number. It doesn't move money, since that money is already in the saved-in account's balance.
- New seam: `goals.account_id → accounts`. `deleteAccount` only checks for transactions, so deleting an account that a goal with no transfers yet points at would hit the FK and crash. It needs a "goals" check too.
- No timestamp filters, so the SQL-timestamp lesson doesn't apply. The no-negative lesson applies: the from account must have the money (locked check, same as debts).
- Activity shows transfers as "Transfer". A goal transfer should read "Goal", like "Bill" and "Debt".
- No `prototypes/` folder. No new shared code is needed, so there are no new unit tests beyond RLS.

## Plan

### 1. Schema and migration
- [x] `db/schema.ts` `goals`: `id`, `user_id`, `name text`, `target bigint` (check `> 0`), `deadline date` (string mode, required), `account_id → accounts` (not null, on delete restrict), `saved_before bigint default 0` (check `between 0 and target`), `created_at`. Add the "own rows" policy and export a `Goal` type.
- [x] `db/schema.ts` `transactions`: `goal_id → goals` (nullable, on delete set null, so deleting a goal keeps its transfers as plain transfers).
- [x] `pnpm db:generate`, read the SQL, `pnpm db:migrate` (dev branch).

### 2. Goals actions
- [x] `app/(app)/goals/actions.ts`, copying `debts/actions.ts`:
  - `saveGoal`: create or edit name, target, deadline, account and saved before. The account must be one of the user's own (FKs skip RLS). Edit is scoped to the user's own row and locks it. It refuses when saved before + transfers > target ("Already saved ₱x. Enter at least that.").
  - `deleteGoal`: own row only. Its transfers stay in Activity.
  - `addToGoal`: takes goal id, from account id, amount and date. Inside one `withUser` transaction it:
    1. Locks the accounts (`loadBalances` with `lock`), then the user's own goal row with `for update`.
    2. Checks the from account is the user's own and isn't the goal's account ("Pick an account other than {goal account}.").
    3. Works out what's left: target − saved before − sum of linked transfers. The amount must be no more than that.
    4. Checks the from account has the money.
    5. Inserts a transfer: from → goal account, `goal_id`, payee = goal name, no category.

    It returns `{ ok, completed: amount === left }`.

### 3. Goals list page (criteria 1, 2)
- [x] `app/(app)/goals/page.tsx`: replace the placeholder with the debts page shape. Load goals joined to their account name with the saved sum (`saved_before + coalesce(sum)` over a left join on `goal_id`), ordered by deadline, plus balances.
  Columns: goal (link to `/goals/[id]`, target under it), deadline, saved in (account name), progress (`GoalProgress` and "₱x of ₱y"), actions (Add money, disabled at target; Edit; Delete).
  Empty states: no accounts (point to Accounts) and no goals yet ("Create a goal: an emergency fund, a trip, a new phone.").
- [x] `app/(app)/goals/goal-form.tsx` (client), copying `debt-form.tsx`:
  - `GoalProgress`: `progressBlocks` + `useCompletedFlash`, label "₱x of ₱y saved".
  - `GoalForm`: name, target, deadline, saved in (account select), already saved. Button "Create goal".
  - `AddMoney`: from account (the goal's account left out of the list), amount defaulting to what's left, date. Calls `announceCompleted` on `completed`.
  - `DeleteGoal`: "Its transfers stay in Activity. This can't be undone."

### 4. Goal detail page (criterion 3)
- [x] `app/(app)/goals/[id]/page.tsx`, copying `debts/[id]/page.tsx`: Suspense, then the user's own goal (`notFound()` otherwise) and its transfers (date, from account, to account, amount; newest first; two account joins like Activity's `toAccounts` alias).
  It shows a back link, the header (name, "Deadline … · Saved in …"), `AddMoney`, the bar with "₱x of ₱y saved" and an already-saved line, and a history table: Date, From, To, Amount. Empty: "No money added yet."

## Leaving out
- Picking a goal in the Activity form, or linking an existing transfer to a goal. Money is added only from Goals.
- Withdrawing from a goal (moving money back out). Not in the brief; deleting the transfer in Activity undoes a mistake.
- Monthly "save ₱x to hit the deadline" suggestions, overdue badges, archiving reached goals.
- Goals on the Overview (T-08) and in first-run setup (T-09).
- A DB check that a transaction has at most one of bill/debt/goal id.

## Open questions (my choices, confirm)
1. Deadline required, as the criterion says. An emergency fund often has none; optional costs nothing if you want it.
2. No saving past the target (same as debts: amount capped at what's left).
3. The saved-in account can be changed on edit. Past transfers keep the account they went to, and history shows it. The alternative is locking it once money has been added.
4. Deleting an account that a goal is saved in is refused until the goal is moved or deleted.
