# T-12: Account history and Activity filters

## Acceptance criteria
- [x] Each account has a history page, opened from the Accounts page, listing every entry that touches it (income, expense, transfer in and out) with the account's running balance after each entry; entries from before a deleted category or payee still show
- [x] The account history and Activity can be filtered by month, a single day, or a date range; on Activity it works together with the type filter
- [x] On Activity, filtering by a type shows only the columns that fit it: expense shows category and payee; income shows source; transfer shows from and to. The "All" view keeps one shared set of columns
- [x] Dates use Asia/Manila, with a unit test at a month boundary and a test that the running balance ends at the account's current balance
- [x] Account balances, Budget and Overview figures are unchanged for the same data (display only, no balance math touched)

## Findings
- No schema change and no migration. Every entry is a `transactions` row with `account_id` and, for transfers, `to_account_id`; an account's history is the rows where either matches. Deleting a category sets `category_id` null and a payee is plain text, so old rows survive and the left join already shows "Uncategorized".
- Accounts with entries can't be deleted (FK `restrict`), so history can't vanish with an account. The audit log and archive are T-13, not here.
- There is **no "source" field on income**. Income uses `payee` (the form's placeholder is "Employer") plus an income category. So "income shows source" has to mean the payee, relabelled "Source" (question 1).
- `balanceOf` ignores order. A running balance needs a chronological order: `date`, then `created_at` (the same tiebreak Activity uses). Back-dated entries can make the running balance dip below zero in date order even though today's balance is not; that is shown as is.
- With a date filter the first visible row must still carry the true balance, so the running balance is computed over all of the account's entries and the filter only hides rows.
- Activity is a single page with `?type=`; the filter nav is Links, so the date filter can be a plain GET form that keeps `type` in a hidden field. No client component needed.
- `lib/money.ts` already has `manilaMonth` and a private `nextMonth`; month ranges build on those. Dates are `YYYY-MM-DD` strings, so range checks are string comparisons in SQL (`gte`/`lte` on the date column), no JS Date.
- `/accounts/[id]` is the third dynamic route (like `/debts/[id]`, `/goals/[id]`): the page body goes inside `<Suspense>`, and the sidebar already lights `/accounts` on sub-paths and is already wrapped in Suspense (lesson 2026-11-13-suspense-around-usepathname).
- Rows on Debts and Goals link through a stretched link on the name (`after:absolute after:inset-0`) because a hover-only underline was not found in T-05; Accounts copies that, with the Edit and Delete buttons staying clickable above it.
- No `prototypes/`. Code graph not needed.
