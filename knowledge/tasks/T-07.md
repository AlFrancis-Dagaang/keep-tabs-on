# T-07: Budget

## Acceptance criteria
- [x] Set optional monthly limits on spending categories; Budget page shows this month's budget, spent and left per category and in total
- [x] Spent counts expenses in spending categories only; payments linked to bills or debts are excluded (unit test)
- [x] Over-budget categories show clay diagonal stripes on their bar
- [x] Each month's limits are snapshotted; past months appear in history with budget, spent and saved per month and per category, and changing a limit doesn't change past months (unit test)
- [x] "This month" uses Asia/Manila dates (unit test around the month boundary)

## Findings
- Arch names `categories.monthly_budget` and `budget_months` (month, category_id, budget). Neither exists yet; `app/(app)/budget/page.tsx` is a placeholder.
- Arch's risk: "the snapshot must be written when a month is first viewed or rolls over; a missed snapshot means history uses current limits". Writing a `budget_months` row **only when a limit is set or changed** removes that risk: a month's limit is the latest row at or before that month. A month nobody opened still gets the right limit, and a change this month never touches earlier rows. Then `categories.monthly_budget` would just duplicate the latest row, so it's left out (an arch deviation; see questions).
- `transactions.date` is a plain `date` the user picked, so "in month M" is a string range on dates, no timestamptz. The SQL-timestamp lesson doesn't apply.
- Bill and debt payments are already expenses with no category, but spent still filters `bill_id is null and debt_id is null` explicitly, so a future categorised payment can't leak in.
- Manila "today" is already computed inline on 6 pages (`Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Manila" })`). Budget needs it as a tested function.
- `PixelBar` turns clay at 12 blocks; it has no over state. Clay is `--clay` / `bg-primary`.
- Deleting a category sets entries' `category_id` to null, so their spend leaves every month anyway. Cascading its `budget_months` rows keeps history consistent with that.
- No `prototypes/` folder. Not a cross-cutting task, so `graphify-out/` wasn't used.

## Plan

### 1. Schema and migration
- [x] `db/schema.ts` `budgetMonths` (`budget_months`): `id`, `user_id`, `category_id → categories` (not null, on delete cascade), `month date` (string mode, first of the month, check `extract(day from month) = 1`), `budget bigint` (nullable: null = limit removed; check `> 0`), `created_at`. Unique `(user_id, category_id, month)`, "own rows" policy, `BudgetMonth` type.
- [x] `pnpm db:generate`, read the SQL, `pnpm db:migrate` (dev branch). 0005 joins backlog item 1 (production migrations).

### 2. Pure budget logic, `lib/money.ts` + `lib/money.test.ts` (criteria 2, 4, 5)
- [x] `manilaMonth(now: Date): string` → `"YYYY-MM-01"` in Asia/Manila. Test: `2026-11-30T15:59Z` → `2026-11-01`, `2026-11-30T16:00Z` → `2026-12-01`.
- [x] `budgetFor(month, categories, limits, expenses)` → `{ rows: [{ id, name, budget | null, spent, left }], budget, spent, left }`.
  - Limit per category = the latest `limits` row with `month <= month` (null if none or removed).
  - Spent = expenses with `date` in that month, `categoryId` in the given spending categories, `billId` and `debtId` null.
  - Totals cover categories with a limit only, so "left" isn't eaten by unbudgeted spending (see questions).
  - Tests: an income, a transfer, a bill payment and a debt payment don't count; an expense on the 1st and the last day counts, the next month's 1st doesn't; adding a limit row for December leaves November's result unchanged.
- [x] `budgetHistory(thisMonth, categories, limits, expenses)` → `budgetFor` for each month from the earliest limit or expense month up to the month before `thisMonth`, newest first, with `saved = budget − spent` (negative = overspent). Rows with no limit and no spend are dropped. Test: two months, one limit change, right per-month numbers.
