# T-15: Activity polish, dates in words and editing entries

## Acceptance criteria
- [ ] Dates: every date the app shows is in words, like "Jan 2, 2027", on Activity, account history, Overview, Recurring bills, Installments, Goals, Debts and Budget, through one helper with a unit test (including a month boundary and a date-only string in Asia/Manila); form date inputs stay native
- [ ] Wording: every user-facing "Delete" is "Remove" (buttons, dialog titles, confirmations, screen-reader labels), on every page; behaviour is unchanged
- [ ] Icons: simple lucide icons on each sidebar page and on the action buttons (Add, Edit, Remove, Pay); every icon-only button has an accessible name
- [ ] Month picker: the From/To inputs and the "This month" and "Last month" pills become a grid month picker (a button showing "November 2026" that opens a year header with previous and next arrows, a 4×3 month grid and a "This month" row); months before the earliest entry and after the current month (Asia/Manila) are dimmed and can't be picked, and the current month is easy to find; From/To stay under a small "Custom range" for single days and ranges; it works with the Activity type filter and on the account history pages
- [ ] Activity time: Activity and the account history list show the time each entry was logged beside its date, from the entry's created time, labelled as logged time; no schema change
- [ ] Edit entries: an income, expense or transfer can be edited from Activity and the account history page (type, account, amount, date, category, payee, note); an edit that would take an account below zero is refused, balances stay correct on both sides of a transfer (including to a name), and entries linked to a bill, debt, goal or installment are not editable; a unit test covers the balance effect of an edit, and the rule is proved on dev
- [ ] Existing entries, balances, Budget and Overview figures are unchanged for the same data; the migration, if any, is additive only

## Findings
- No migration: the logged time comes from `transactions.created_at` (timestamptz, already there). `transactions.date` is a plain date, so there is no true time of purchase; the time shown is when the entry was logged, and an edit keeps it.
- Dates render raw (`row.date`, `nextDueDate`, `deadline`) in 13 places: Overview (2), Activity, account history, Debts list and `/debts/[id]` (2), Goals list and `/goals/[id]` (2), Bills, Installments. Budget already has a local `monthName` helper ("November 2026") in `app/(app)/budget/page.tsx`; keep it, it is already words.
- "Delete" is in 8 forms: accounts, activity, bills, debts, goals, installments, settings (categories). Each has the trigger button, dialog title and submit button ("Delete debt"). Server actions keep their `delete…` names (code, not user-facing).
- `lucide-react` 1.70.0 and `radix-ui` 1.8.1 are installed. `components/ui/` has no Popover yet; CLAUDE.md adds shadcn components with `pnpm dlx shadcn@4.23.0 add popover`. The sidebar is text-only.
- Editing has a pattern to copy: `AccountForm` is "Add" without an `account` prop and "Edit" with one (hidden `id` input, same action). `saveEntry` only inserts today.
- Balance safety: `saveEntry` and `deleteEntry` already lock accounts with `loadBalances(tx, userId, { lock: true })` and check `>= 0`. An edit can lower any of three accounts (old account, new account, new transfer target) and can raise the credit side of an old income/transfer, so the check must recompute every account with the entry swapped, not just the paying one.
- Linked entries (billId, debtId, goalId, installmentId set) drive due dates, goal and debt progress. Editing one would desync those, and deleting one already doesn't un-roll a due date (known follow-up). They stay read-only.
- Budget and Overview figures are computed from entries, so an edit flows through with no extra code. Bill cycles compare `created_at`, which an edit does not touch (lesson 2026-11-11).
- `parseRange` / `monthRange` already turn a month into `from`/`to`, so the picker can stay URL-driven and no server filtering changes.
- Account history (`/accounts/[id]`) already shares `DateFilter`, so the picker lands there with the same component. It loads all of an account's entries, so its earliest month comes free from the rows; Activity needs one `min(date)` query.
