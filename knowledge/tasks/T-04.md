# T-04: Recurring bills and pixel progress bar

## Acceptance criteria
- [x] Create a bill with amount, next due date and repeat (weekly, every 2 weeks, monthly, every 3 months, yearly); due date editable anytime
- [x] Record payment from an account (partial allowed): an expense linked to the bill is saved, and the bill's 12-block progress bar fills by the paid share of this cycle
- [x] Paying the cycle in full rolls the next due date in the same DB transaction; unit tests cover each repeat, including Jan 31 → Feb 28/29
- [x] Progress bar matches docs/design.md: drop-in blocks, clay when complete, flash on completion, no animation under reduced motion
- [x] Overdue bills show a clay warning badge

## Findings
- Arch already names the shape: `bills` (name, amount, next_due_date, repeat) and an optional `transactions.bill_id`. Progress is computed from transactions, never stored.
- "This cycle" needs a boundary. Payments link to the bill; the bill keeps `cycle_start` (a timestamp, set to now() on each roll). Paid this cycle = sum of linked expenses created after `cycle_start`.
  Editing the due date leaves the paid amount alone, and deleting a payment from an earlier cycle doesn't touch this one.
- Monthly roll: Jan 31 → Feb 28 → Mar 28 would drift if we rolled from the clamped date. The bill keeps `due_day` (the day of the month the owner picked) and rolls to that day, clamped to the month's length. So Jan 31 → Feb 28/29 → Mar 31.
- A bill payment is an expense with no category (the brief says bill payments don't count toward budgets) and the bill's name as payee. Activity shows "Bill" in the Category column for these instead of "Uncategorized".
- The lesson applies: a payment can't take the account below zero. Reuse the `loadBalances(..., { lock: true })` check from `saveEntry`.
- FKs skip RLS: `payBill` must confirm both the bill and the account belong to the user.
- Dates use Asia/Manila (same `Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Manila" })` as Activity). Overdue means `next_due_date < today`.
- Tailwind v4, no animation setup yet. Keyframes go in `app/globals.css`; `motion-safe:` turns animation off under reduced motion.
- The pixel bar is shared: goals and debts use it later (T-05, T-06). So it goes in `components/`, not in the bills folder.
- No `prototypes/` folder.

## Plan

### 1. Schema and migration
- [x] `db/schema.ts` `bills`: `id`, `user_id`, `name text`, `amount bigint` (check `> 0`), `next_due_date date` (string mode), `due_day smallint` (check 1–31), `repeat text` (check `in ('weekly','biweekly','monthly','quarterly','yearly')`), `cycle_start timestamptz default now()`, `created_at`. Add the "own rows" policy and export a `Bill` type.
- [x] `db/schema.ts` `transactions`: `bill_id → bills` (nullable, on delete set null, so deleting a bill keeps its payments as plain expenses).
- [x] `pnpm db:generate`, read the SQL, `pnpm db:migrate`.

### 2. Pure logic (tested)
- [x] `lib/money.ts` gets two functions:
  - `nextDueDate(date, repeat, dueDay)`: weekly +7 days and biweekly +14. Monthly, quarterly and yearly add 1, 3 or 12 months and land on `dueDay`, clamped to the month's length. Works on `YYYY-MM-DD` strings in UTC, so the server's time zone can't shift the date.
  - `billBlocks(paid, amount)`: `Math.min(12, Math.floor(paid * 12 / amount))`. A block fills only once it's earned; all 12 only when the bill is fully paid.
- [x] `lib/money.test.ts`: one test per repeat. Also Jan 31 → Feb 28 (2027) and Feb 29 (2028), Feb 28 → Mar 31 with `dueDay` 31, Nov 30 quarterly → Feb 28, Dec 31 weekly → Jan 7 across the year, Feb 29 yearly → Feb 28. `billBlocks` at 0, a partial share, just under full, and full.

### 3. Pixel progress bar (criterion 4)
- [x] `app/globals.css`: two keyframes, `drop` (falls in from above) and `flash` (a short opacity blink), registered as `--animate-drop` and `--animate-flash` in `@theme`.
- [x] `components/pixel-bar.tsx` (client): 12 square blocks, 11px each, 3px gaps, no rounding. Filled blocks are `bg-foreground`, empty ones `bg-border`, and all filled blocks turn `bg-primary` when complete.
  Each filled block uses `motion-safe:animate-drop`, with an animation delay of index × 40ms. With `flash`, the bar gets `motion-safe:animate-flash`.
  `role="progressbar"`, `aria-valuenow` and `aria-valuemax=12`, plus an `aria-label` the caller passes in.
  Props: `blocks`, `label`, optional `flash`.
  Over-budget stripes belong to T-07, not planned here.

### 4. Bills actions
- [x] `app/(app)/bills/actions.ts` gets three actions, in the same style as `activity/actions.ts` (Zod, `FormState` with values and errors, `refresh()`):
  - `saveBill`: create or edit name, amount, next due date and repeat. Sets `due_day` from the picked date, so editing the date resets the anchor. Edit is scoped to the user's own row.
  - `deleteBill`: own row only. Its payments stay in Activity.
  - `payBill`: takes bill id, account id, amount and date. Inside one `withUser` transaction it:
    1. Locks the accounts with `loadBalances(tx, userId, { lock: true })`, then locks the user's own bill row with `for update`.
    2. Checks the account is one of the user's own.
    3. Works out what's left this cycle: amount − paid since `cycle_start`. The payment must be above zero and no more than what's left, so the bar never passes full.
    4. Checks the account has the money (>= 0 rule).
    5. Inserts the expense with `bill_id`, payee = bill name, no category.
    6. If the cycle is now fully paid, updates `next_due_date = nextDueDate(...)` and `cycle_start = now()`.

    It returns `{ ok, completed }`, and the bar flashes only when `completed` is true.

### 5. Bills page (criteria 1, 2, 5)
- [x] `app/(app)/bills/page.tsx`: the Suspense pattern from Activity. It loads the bills (ordered by next due date), each bill's paid-this-cycle sum (one grouped query: linked expenses where `created_at > cycle_start`), and the balances for the pay form.
  Table columns: name, amount, repeat, next due, progress (`PixelBar` plus "₱x of ₱y"), and actions.
  Overdue (`next_due_date < today`) shows a clay pill reading "Overdue" next to the date.

- [x] `app/(app)/bills/bill-form.tsx` (client), copying the patterns in `entry-form.tsx`:

  - `PayBill` is a modal titled "Record payment". It has an account Select showing balances, an amount defaulting to what's left this cycle, and a date defaulting to today.
    When `completed` comes back, the row's bar shows 12 clay blocks with `flash` for about 1s, then `refresh()` shows the new cycle's empty bar.
  - `DeleteBill`.

## Leaving out
- Pausing bills (brief: out of scope).
- Bills on the Overview, and "due in 7 days" (T-08).
- Linking an existing Activity entry to a bill, and picking a bill from the Activity form. Payments are made only from Bills.
- Un-rolling a cycle when one of its payments is deleted later. The due date stays rolled; the owner can edit it.
- Over-budget stripes (T-07).

## Open questions (my choices, confirm)
1. `due_day` anchor so monthly bills on the 29th–31st don't drift to the 28th. This costs one column. Without it the code is a little smaller, but a bill due on the 31st moves to the 28th forever after February.
2. A payment can't be more than what's left this cycle (no prepaying the next cycle).
3. Editing a bill's amount below what's already paid this cycle is refused ("Already paid ₱x this cycle"), so editing never quietly rolls a cycle.
4. Bill payments have no category and show as "Bill" in Activity.
