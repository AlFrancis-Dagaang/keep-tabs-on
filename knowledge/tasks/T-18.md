# T-18: Edit or undo bill, debt, goal and installment payments

## Acceptance criteria
- [x] Design first: a decision in `knowledge/decisions/` says which fields of a linked payment can change, and what happens to the bill's or installment's next due date and to debt and goal progress on an edit and on a remove. I approve it before any code
- [x] A payment can be edited from its row in the history on its bill, installment, debt or goal page (amount, date, account, note). Progress and the next due date follow the edit; an edit that would take an account below zero is refused
- [x] Removing a bill or installment payment rolls the next due date back when that payment was the one that rolled it; debt and goal progress follow a remove, as today
- [x] Linked rows on Activity either get the same edit or keep their read-only rule, as the decision says. A unit test covers the due-date and progress effect, the rules are proved on dev with the real actions, and the migration, if any, is additive only

## Findings
- **How a payment drives state today.** A linked payment is a `transactions` row with `billId`, `installmentId`, `debtId` or `goalId`.
  - Bill: "paid this cycle" is the sum of payments with `created_at > bills.cycleStart`, compared in SQL. The payment that fills the cycle runs, in the same transaction, `nextDueDate = nextDueDate(...)` and `cycleStart = now()`, so its `created_at` equals the new `cycleStart` and it counts toward the cycle it closed. That equality is the only trace of "the payment that rolled it".
  - Installment: paid = `paidBefore` + count of payments. Every payment except the last rolls `nextDueDate` one month. Payment amounts are not used for progress.
  - Debt: left = `total - paidBefore - sum(payments)`. Goal: left = `target - savedBefore - sum(transfers into the goal account)`.
- **Gap that exists today.** `deleteEntry` (Activity) already removes linked rows. It checks only that the credited account stays >= 0. It never rolls a due date back, so removing the payment that closed a bill cycle leaves the bill on the next cycle with the old one unpaid. T-15 recorded this as a known follow-up. Removing from Activity must go through the new rule too, or the two removes disagree.
- **Why a marker is needed for bills.** Rolling back needs the previous `cycleStart`. It is not derivable: bills can change amount, and the earlier roller is not marked. The previous due date, on the other hand, is exactly invertible from `repeat` and `dueDay` (monthly/quarterly/yearly land on `dueDay` clamped, weekly/biweekly subtract days). So the only new stored fact is one nullable timestamp on the rolling payment: the `cycleStart` it replaced. Installments need no marker: they are monthly, and the due date follows the payment count.
- **Edit already has most of its parts.** `balancesAfterEdit` (lib/money.ts) rechecks every account after a change, `loadBalances(..., { lock: true })` locks them, `saveEntry` shows the pattern including the "FKs skip RLS, find the account among the user's own" guard. `isLinked` is what makes Activity read-only.
- **UI seams.** `components/payment-history.tsx` (bills, installments) is a server component with Date, Paid from, Note, Amount and no actions cell. Debts and Goals detail pages have their own tables (T-17 left them). `RowActions` + `RowMenu` (components/row-menu.tsx) already give desktop buttons plus the mobile corner "⋯", and `DeleteEntry` is the existing confirm dialog (text is entry-specific).
- **Lessons that apply.** 2026-11-11 (compare timestamps in SQL: the roller is found by a SQL join `created_at = cycle_start`, and the marker is written with a subselect, never a JS Date), 2026-11-13 (tests write the bill and its payment in separate `withUser` calls), 2026-11-10 (balances stay >= 0), 2026-11-16 (show a mock of any new placement first: below).
- **Design input.** The second mock image (owner-approved structure): mobile card with a corner "⋯" opening Edit and Remove; Edit payment dialog with Amount, Date, Paid from, Note, Cancel and Save; the error under Amount "This would take BPI below zero. ..."; Remove dialog "Remove this payment?" with one line saying what changes. It shows no desktop row, so that placement is mocked below.
- `prototypes/` has no file covering T-18. No code graph needed.

## Proposed rules (the decision to approve in step 1)
Editable on all four: amount, date, account, note. Not editable: which bill, debt, goal or installment it belongs to, type, payee. The due date and cycle never follow a payment's date field; they follow the cycle and the count.

| | Edit | Remove |
|---|---|---|
| Bill, payment in the current open cycle | Amount may change as long as the cycle's total stays below the bill amount (an edit can't finish a cycle; "Record payment" does that). Date, account, note free | Cycle total drops; no date change |
| Bill, the payment that closed the last cycle (the roller) | Amount locked (shown disabled with a hint); date, account, note free | Rolls back: due date steps back by one repeat, cycle reopens with the stored previous `cycleStart` |
| Bill, older closed-cycle payment | Amount locked; date, account, note free | Removed; no date change (it did not roll the current date) |
| Installment | Amount free (> 0): progress counts payments, not pesos; date, account, note free | Count drops by one and the due date steps back one month. If it was the final payment (which did not roll), the due date stays |
| Debt (owe: expense; owed: income) | Amount free while the total of payments stays <= total - paid-before; account, date, note free | Progress follows; refused if it would take the receiving account below zero (as `deleteEntry` does today) |
| Goal (transfer into the goal's account) | Amount free while the total stays <= target - saved-before; the "from" account can't be the goal's account; date, note free | Progress follows; same below-zero refusal |

Every edit rechecks all accounts with `balancesAfterEdit` and refuses with "This would take X below zero." Activity: linked rows keep their read-only Edit (edit from the bill, installment, debt or goal page); Remove stays on Activity but runs the same rule, so due dates roll back from either place.

## Open questions for you
1. **Bill amount rule.** I propose that a bill payment's amount is editable only in the current open cycle and can't reach the bill amount; the payment that closed a cycle and older ones have the amount locked (remove and re-record instead). Alternative: let an edit also finish or reopen a cycle, which is more code and more ways to be wrong. OK with the locked version?
2. **Installment amount.** Free to edit (progress counts payments, not pesos). Should it instead stay locked to the monthly amount?
3. **Old rollers.** A bill cycle closed before this task has no stored previous `cycleStart`; I propose refusing to remove it with a clear message. Alternative is a guess that can inflate "paid this cycle". Number of such rows on dev is unchecked; I'd count them (host checked first) when applying. OK to refuse?
4. **Activity.** Keep Edit read-only there and Remove allowed with the same roll-back (my proposal), or give Activity the same Edit?
5. **Migration.** One nullable column on `transactions` is the only schema change; confirm that is acceptable (the criterion allows an additive one).
