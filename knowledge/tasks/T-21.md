# T-21: Set aside before tracking

## Acceptance criteria (copied from `docs/tasks.md`)
- [x] Field: the bill, debt, installment and goal forms have an optional "Set aside before tracking" amount, next to "Already saved" or "Paid before tracking" where one exists (one additive `set_aside_before` column per table, default 0, never negative); "Already saved" and "Paid before tracking" keep feeding the Saved and Paid bars and Overview exactly as today
- [x] Figures: the amount is added into that item's Set aside bar and figure. Goals and debts: it counts for good, like their running sum. Bills: it counts until the cycle rolls. Installments: it counts only until the next payment. The Set aside bar shows when the amount is above zero even with no linked transfer; the two figures are still never added, and Overview does not show Set aside
- [x] No side effects: no Saved, Paid, due date, installment count, account balance, budget or net worth changes. A DB-backed test on dev proves that, and that paying an installment or rolling a bill's cycle drops its pre-tracking amount while goals and debts keep theirs
- [x] `pnpm lint`, `pnpm test` and `pnpm build` pass; the migration is additive and applied to dev only after the DB host check; looked at signed in on dev on all four kinds, at 390px (no sideways scroll) and desktop

## Findings
- Every list and detail page already selects its figure from one helper in `lib/set-aside.ts` (`billSetAside`, `debtSetAside`, `goalSetAside`, `installmentSetAside`) and shows the bar when the figure is above zero. Adding the pre-tracking amount inside those four helpers changes all eight pages and the DB tests with no page edits. The pages stay as they are.
- Goals and debts: the figure is `linked transfers + set_aside_before`. Nothing to reset.
- Bills and installments reset (bills at the cycle roll, installments at the next payment), and T-18 lets the owner remove a payment, which reopens the cycle. If a roll or payment zeroed the column, a remove could not bring it back, and `payBill`, `payInstallment`, `deleteEntry` and `editPayment` would all need edits. Instead the amount is stamped with when it was saved (`set_aside_before_at`) and counted only while nothing has happened since: a bill counts it while `cycle_start <= set_aside_before_at`; an installment counts it while no installment payment is newer than `set_aside_before_at`. A remove then restores it for free, and pay and undo code stays untouched. The stamp is set only when the amount changes (not on every save), so renaming a bill after a roll can't revive an old amount.
- Timestamps are compared in SQL (lesson 2026-11-11). Seeding a cycle roll and the stamp in the DB test needs separate `withUser` calls (lesson 2026-11-13, now() is fixed per transaction).
- Raw correlated SQL names the outer table in full (lesson 2026-11-17, qualify the outer table). The helper already does; the new terms follow it.
- `goals_saved_before` caps "Already saved" at the target; the new amount has no cap, because the Set aside figure may already exceed its target and shows the real number (T-20).
- Form fields are plain `Field` + `Input` blocks (goal-form 69, debt-form 83, installment-form 61, bill-form 63-70); the actions parse them with a zod transform like `savedBefore` (goals/actions.ts 35). Saves read the current row `for update` first, which is where "did the amount change" is known.

## Real-data example (lesson 2026-11-14), owner's figures from the T-20 handoff
- Therapy goal (target ₱2,500): linked ₱1,000 today. Entering ₱1,500 as set aside before tracking makes Set aside ₱2,500 / 2,500 (bar full). Saved stays whatever "Already saved" says (₱1,500 if you set it); the two are never added.
- Claude Code bill (₱1,400): linked ₱100 today. Entering ₱300 shows Set aside ₱400 / 1,400 until the cycle rolls, then back to linked transfers only.
- Iphone installment (next ₱1,957.92): linked ₱1,000 today. Entering ₱500 shows ₱1,500 until the next payment, then ₱0 from that amount.
- Electric Meter debt (₱1,400): linked ₱700. Entering ₱200 shows ₱900 for good.
